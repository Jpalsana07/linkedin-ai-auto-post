Server components are a tradeoff.

I was building a production app in Next.js with React on the front end.
The question was simple: what should render on the server, and what should wait for the browser?

That choice matters because it changes how fast the first screen appears, how much code ships to the user, and how painful debugging becomes.

The tradeoff is real.
More server rendering can mean less JavaScript and a faster first load.
More client rendering can mean simpler state, easier interactions, and fewer surprises when things update on the page.

I chose a mostly client-heavy setup for the parts that changed often.
Why? The app had live dashboards, forms, and frequent state updates.
The hidden constraint was developer speed.
When a screen changes every few days, splitting logic across server and browser can slow down every small edit.

So I kept server rendering for the initial page and shared data, then moved interactive pieces to the browser.

That choice would not fit every app.
If the page is mostly static, or search visibility matters more than rapid UI changes, I would push harder toward server rendering.

The lesson: optimize for the shape of change, not just raw performance.
