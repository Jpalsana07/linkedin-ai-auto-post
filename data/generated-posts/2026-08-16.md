# LinkedIn Post

Topic: TypeScript Pitfalls

Date: 2026-08-16

---

TypeScript isn't your safety net.

Teams love to say it catches bugs before prod.
It does.
But it also lets bad architecture feel polished.

I saw this on a billing app we shipped last year.
We had 18 files of types, Zod validation, and strict mode on.
The code looked disciplined.
The invoices still broke.

Not because TypeScript failed.
Because we had modeled the wrong thing.
We were encoding every edge case in the type system instead of making the flow simpler.

After we deleted 400 lines and moved the logic into 3 plain functions, the bug count dropped fast.
The next release had zero invoice regressions.

That was the hard lesson:
TypeScript is best at protecting a clear design, not rescuing a messy one.

The strongest counterargument is real:
for large teams, types keep refactors safe and make APIs harder to misuse.
I still want that.

But if the code only works because the types are doing emotional labor for the architecture, the design is already tired.

Where have you seen TypeScript hide a bad design instead of fixing it?
