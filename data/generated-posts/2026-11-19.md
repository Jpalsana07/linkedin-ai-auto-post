Topic: MCP and Context Engineering

Date: 2026-11-19

The bot knew too much.

I was building a support assistant for a client project, and it kept giving confident answers from the wrong files.

The setup used MCP, the model context protocol that lets tools share data, and a RAG search layer, which pulls in relevant docs before the model answers.

The first version felt smart.
It could read tickets, fetch docs, and draft replies.

But one tiny thing kept breaking trust:
the model saw every tool and every document, even when it only needed one or two.

So it started mixing old policies with new ones.
It quoted a retired note once.
It stitched two unrelated answers together another time.

I spent 2 hours trimming the context.
Not by adding more prompts.
By sending less.

I narrowed the tool schema, the menu of actions the bot can take.
I split documents by task.
I made the assistant ask for one missing piece instead of loading the whole archive.

The root cause was simple:
I had treated context like storage.
It is not storage.

Context is working memory.
If you fill it with noise, the model becomes confident in the wrong thing.

The lesson: with MCP, the best system is not the one that can see everything.
It is the one that sees only what it needs.

Where have you seen a system fail because it knew too much?
