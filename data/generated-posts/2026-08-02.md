# LinkedIn Post

Topic: Node.js at Scale

Date: 2026-08-02

---

One queue changed everything.

We were running a Node.js API that had to serve checkout, emails, and a few slow reports.
If one request got stuck, the whole server felt it.

The decision was simple: do we process work immediately inside the request, or send it to BullMQ, a background job queue?

Immediate work is easy to reason about.
The user clicks, the server does the thing, the response comes back.

But at scale, that means every slow task competes with live traffic.
A 2-second PDF export can sit next to a 50-millisecond checkout call and make both feel broken.

We chose the queue.

Not because queues are elegant.
Because our real constraint was bursty traffic, not code style.

At peak, we saw 300+ jobs pile up in under a minute.
With BullMQ, checkout stayed fast even when reports lagged behind by 10 minutes.
That delay was acceptable.
A slow payment flow was not.

The lesson: protect the user-facing path first, even if the back office gets messier.

This tradeoff does not apply when the work must finish before the user can move on, like a bank transfer or a password reset.

Where have you seen a background queue save the day, and where did it just add complexity?
