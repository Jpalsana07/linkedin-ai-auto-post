Topic: MCP and Context Engineering

Date: 2026-11-28

---

MCP won the comparison.

I was wiring an AI helper into a production app, and the real problem was simple:
how do you give the model the right tools without handing it the whole house?

I tried two approaches.

First was plain prompt stuffing, where I pasted docs, endpoints, and examples into the message.
It worked once, then got flaky as the context grew.
After about 8 tool calls, the responses started drifting, and token use kept climbing.

Then I switched to MCP, the Model Context Protocol — a standard way to expose only the tools and data the model needs.
Instead of dumping everything into context, I gave the model a narrow menu of actions.

The difference was immediate.
The tool list stayed small.
The prompts stayed shorter.
And the agent stopped guessing which API to call.

I also tried LangChain, the orchestration layer for LLM apps, for the same job.
It was useful for chaining steps, but for tool access itself it felt heavier than I needed.
More moving parts.
More code to keep aligned.

My lesson:
context engineering beats context dumping.
The model performs better when you design the room it works in, not when you keep throwing more furniture inside.

For tool use in production, MCP was the cleaner win.

Where have you seen “more context” make an AI worse?
