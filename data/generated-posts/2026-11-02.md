Agent reliability is mostly theater.

The popular advice is to add more checks, more planners, more retries, and more agents until the system feels “robust.”
That sounds safe.
It also makes failure harder to see.

I hit this building an automation pipeline with Claude API and a small tool layer.
The agent could read a document, decide what to do, and call the right function.
It looked solid in tests.

Then one branch started looping on the same stale input.
Nothing crashed.
The logs stayed tidy.
The only clue was a task that quietly took 14 minutes instead of 40 seconds.

The fix was not another agent.
It was a hard timeout, a single allowed retry, and a plain status that said “stuck on the same step.”

That’s the contrarian part:
reliability usually comes from fewer moving parts, not smarter ones.

The strongest counterargument is obvious.
Some workflows really do need planning, retries, and multiple passes, especially when the input is messy.
I agree.

But if the system can’t tell you when it is confused, extra intelligence just hides the confusion longer.

The lesson: make agent failures obvious before you make them clever.

Where have you seen “more AI” make a workflow less trustworthy?
