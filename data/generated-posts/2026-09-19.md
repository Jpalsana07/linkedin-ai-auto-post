# LinkedIn Post

Topic: TypeScript Pitfalls

Date: 2026-09-19

---

Types erased a bug.

We were building a TypeScript backend for a small checkout flow.
The goal was simple: catch bad data before it reached Stripe.
One wrong field in production meant a real customer couldn’t pay.

The question was whether to trust TypeScript alone, or add runtime validation too.
TypeScript checks code while you’re writing it.
Runtime validation checks the actual data after the app is running.

That sounds like overlap.
It is.

We chose Zod, a schema validator, on the edges of the app.
That meant every request body got checked twice: once by TypeScript in the editor, once by Zod at runtime.

The tradeoff was extra code and a little friction.
But the constraint most people miss is this:
TypeScript disappears after build.
The API still receives JSON from browsers, scripts, and broken clients.

One malformed payload can slip through perfect types.

So I’ll take the duplication when the input is external.
I won’t add it everywhere inside the app, where the data already comes from code I control.

That’s the line for me:
validate at the boundary, not in every room.

Where do you draw that line between compile-time safety and runtime checks?
