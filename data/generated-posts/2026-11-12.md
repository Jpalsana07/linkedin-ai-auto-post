A faster answer cost me more.

I was adding an LLM feature to a production web app.
The choice was simple on paper: stream the answer token by token, or wait and send one complete response.

Streaming feels better.
The user sees words arrive in under a second.
It also makes the app look alive while the model is still thinking.

But the hidden cost is state.
If the model changes its mind halfway through, you have to handle partial text, retries, and weird edge cases in the UI.
With one complete response, validation is easier.
You can check the output, clean it up, and show only what passed.

I chose the complete response path for that build.
Not because streaming is bad.
Because the feature had a strict formatting rule, and I needed the answer to survive a parser before it reached the screen.

That constraint mattered more than perceived speed.
A 300 ms delay is forgivable.
A broken response that looks instant is not.

So my rule is simple:
stream when the user is reading for comfort.
Wait when the output must be correct first.

This tradeoff changes when the model is just chatting, or when the UI can safely recover from partial text.

Where do you draw the line between fast and safe?
