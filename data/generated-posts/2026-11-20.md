# LinkedIn Post

Topic: Agent Reliability

Date: 2026-11-20

---

I made the agent stricter on purpose.

Most people think reliability means giving an agent more tools, more memory, and more freedom.

Hot take: agent reliability usually improves when you remove choices.

I was building an agent-driven workflow that reviewed code, checked a few files, and wrote a short summary.
The first version had 8 tools and a loose prompt.
It looked smart in demos and drifted in real use.

One run would call the wrong tool.
Another would loop twice before finishing.
A third would return a confident answer with a missing step.

I cut it down to 3 tools, added a tool schema — the menu of actions the bot can take — and forced a fixed path for the common case.
I also made Claude Code do the boring part: draft, review, and test the changes before anything shipped.

The result was less impressive on paper and far more useful in practice.
Fewer branches.
Fewer weird failures.
Less time spent wondering what the agent was “thinking.”

The strongest counterargument is obvious: constrained agents can feel less capable, especially when the task is messy.
That’s true.
For open-ended work, flexibility matters.

But for production, I want an agent that is predictable first and clever second.

Reliability is usually a design problem, not an intelligence problem.

What have you seen break first: too little freedom, or too much?
