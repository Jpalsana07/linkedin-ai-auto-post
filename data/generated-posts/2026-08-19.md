12 million requests later

I’m building a Node.js API for B2B teams that need fast, reliable automation.
This week, I shipped the first version that can handle customer workloads without falling over.

The change looked small on paper.
We split one service into 3 Node.js workers, added Redis for queueing, and moved our slowest job off the request path.

Before that, one spike could pin the CPU at 100% and turn a 300ms request into a 9s timeout.
After the deploy, p95 latency dropped from 1.8s to 410ms.
Error rate fell from 4.2% to 0.6%.

But it’s not done.

Memory still climbs after long runs.
That means one of our background jobs is holding onto objects longer than it should.
Node is great at moving fast.
At scale, the real work is learning where your code quietly keeps paying interest.

The lesson I keep relearning: in Node.js, speed comes from removing pressure, not adding more code.

What’s the first thing you’d simplify when a Node service starts slowing down?
