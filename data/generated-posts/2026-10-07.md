# LinkedIn Post

Topic: TypeScript Pitfalls

Date: 2026-10-07

---

TypeScript made us slower.

We were building a checkout flow in a Next.js app.
The bug wasn’t obvious.
The code looked safe, but one missing field broke a payment path for real users.

The decision was simple:
write stricter types everywhere, or keep some parts loose and move faster.

Strict TypeScript catches small mistakes early.
That matters when one bad object can turn into a broken invoice or a failed signup.
But it also adds friction.
Every API change means touching types in 6 places.
Every third-party package with weak typings becomes a little fight.

We chose a middle path.
Core money code stayed strict.
UI and integration edges used lighter types, plus runtime checks.
That kept the checkout stable without turning every small edit into a type puzzle.

The constraint most people miss is team speed.
A type system only helps if people still want to ship in it.
If reviews start stalling on types instead of product work, the safety net becomes drag.

This tradeoff doesn’t apply everywhere.
For a library, a compiler-enforced API is worth the extra work.
For a small product team shipping weekly, fewer perfect types can mean better real-world reliability.

Where do you draw the line between type safety and shipping speed?
